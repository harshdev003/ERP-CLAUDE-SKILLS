# Architecture

## Source layout (`src/`)

| Path | Purpose |
|---|---|
| `main.py` | CLI entry point (the `livekit.toml` entrypoint). Loads `.env`, validates config, starts the LiveKit worker. |
| `entrypoint.py` | Thin per-session orchestrator: builds the per-session `Context`, resolves config (`sessions.SessionResolver`), creates LLM/TTS/STT, builds the agent (`agents.create_agent`) + session (`sessions.SessionManager`), wires metrics, then starts and greets. The LiveKit `JobContext` is passed explicitly to the collaborators that need it. Each concern lives in its own package (below). |
| `agents/` | The voice agent: `base.py` (`BaseAgent` — shared base, mirrors the TTS/STT/LLM provider bases) + `aurie.py` (`Aurie`) + `manager.py` (`AgentManager`, the `create_agent()` seam) which assembles the prompt-parameters block and constructs the agent from a registry. Generation flows through the session LLM (`BaseAgent.llm_node` is a pass-through that only reports when a generation completes, for `agent_reply_saved`); per-turn params are embedded under `** Prompt Parameters:**` for the Aura backend to parse. |
| `llm/` | Builds the session LLM: `manager.py` (`LLMManager` / `create_llm()`) — today always Aura's OpenAI-compatible endpoint via the stock plugin; the single seam for a future multi-provider LLM. `prompt_parameters.py` is the `PromptParameters` dataclass (`.to_dict()` renders the JSON block). |
| `sessions/` | All per-session concerns, one class per file: `session_config.py` (`SessionConfig` dataclass), `session_resolver.py` (`SessionResolver` — connects to the room and resolves config in priority order job/`AGENT_METADATA` → env; `user_id` also falls back to the participant identity, and participant metadata is never read for config → env, enriching the `Context`), `session_manager.py` (`SessionManager` — builds, wires and starts the `AgentSession`, then greets), `background_audio.py` (`build_background_audio()` — builds the optional ambient/thinking `BackgroundAudioPlayer` from config, gated by `AGENT_BACKGROUND_AUDIO_ENABLED`). `SessionManager` keeps only what mutates session-lifecycle state (the away/reconnect/no-participant watchdogs, audible-failure handling, detached-task reaping); three concerns that had accumulated on it sit beside it — `turn_detector_recovery.py` (`TurnDetectorRecovery` — re-probes the cloud turn detector after the SDK's one-way fallback to the local model, via the public `update_options(turn_detection=...)`), `stt_stall_recovery.py` (`SttStallRecovery` — classifies a `user_transcription_timeout` as a real stall or as audio we withheld on purpose, and reconnects an STT stream that has gone silent, owning the seven pieces of bookkeeping that needs), `observability_events.py` (`register_observability_events()` — the monitoring-only handlers, split out because alone among the four event groups they touch no session state), `session_options.py` (`resolve_noise_cancellation()` / `resolve_record_kwargs()`), `stuck_speech_watchdog.py` (`StuckSpeechWatchdog` — while the agent is `speaking`, if the room audio source has held nothing and the TTS node has produced no frame for `AGENT_SPEECH_STUCK_TIMEOUT`, logs `AGENT_SPEECH_STUCK` with the sink's state and interrupts the speech; without it the runtime held that state for minutes, the user's speech went untranscribed, and the app's idle timer ended the call), `messages.py` (the lines the session speaks on its own behalf, not through the LLM) and `reply_saved_notifier.py` (`ReplySavedNotifier` — decides when to publish `agent_reply_saved`: once per generation that has both completed and started being spoken). Both collaborators take the manager's **logger**, not one of their own: the logger name is the `component` field, so a new name would silently move those rows out from under the existing Cloud Logging queries. |
| `tts/` | OO TTS package: `base.py` (`TTSProvider` ABC), `manager.py` (`TTSManager`), one `*_provider.py` per provider (ElevenLabs / OpenAI / Cartesia / Inworld / Fish Audio); `create_tts_provider()` in `__init__.py`. `resolve_tts()` (same module) is the fail-fast entrypoint seam and wraps the primary in a `FallbackAdapter` with the optional `TTS_FALLBACK_PROVIDER` backup for auto-failover. `settings_keys.py` (`TTS_SETTING_KEYS`) is the shared tuning-key list;  `availability.py` (`register_tts_availability_logging`) logs `FallbackAdapter` availability changes and registers on the session's TTS so a silent backup-provider switch is logged. |
| `stt/` | OO STT package mirroring `tts/`: `base.py` (`STTProvider` ABC), `manager.py`, and `deepgram_inference_provider.py` — Deepgram models through LiveKit Inference, `inference.STT(model="deepgram/<model>")`, with an optional server-side `fallback` model. The direct-plugin transport was removed in ENG-1263 once the trial was accepted, so the registry has one entry; `language.py` (`language_for_locale()` — the nova-3 locale mapping) stays a module-level helper rather than a base-class method so a future non-Deepgram provider doesn't inherit it; `create_stt_provider()` in `__init__.py`. An unrecognized `STT_PROVIDER` is fatal at startup — `KNOWN_STT_PROVIDERS` in `config/stt.py` is pinned to `STTManager._REGISTRY` by a unit test, since `src/config` cannot import `src/stt`. Stall **detection** logs `consecutive_stalls`; **recovery** lives in `sessions/stt_stall_recovery.py` and reconnects through the public `session.clear_user_turn()`, which rebuilds the STT stream on a new Inference websocket. The plugin-era reset called the stream's `update_options()`, which on Inference only sends a `session.update` over the same socket, and the gateway's server-side fallback never sees a socket that stays open and goes quiet, because the SDK's receive loop has no timeout. **The provider key keeps its `-inference` suffix on purpose:** it is logged per turn as `stt_provider`, and the Aurie cost store decides which vendor billed the day by matching `inference` in that value. |
| `tools/` | Client-side tools (mirrors the ElevenLabs client tools for the LiveKit transport): `client_tools.py` (`build_client_tools()` seam — `endOnboarding` / `createInsightCard` / `endConversation`, names mirroring the backend prompter's client tools; `endConversation` is minted by the backend from a reply sentinel rather than called by the model) + `publisher.py` (`ClientToolPublisher` — forwards a tool call to the client as a `tool_call` data message). The backend prompter decides when to call them and streams the `tool_calls`; the agent forwards them to the client. Gated by `AGENT_CLIENT_TOOLS_ENABLED` — **on** in `.env.sample` and the deployed secrets (the code default, var absent, is still off). Full contract + backend behavior: `docs/client-tools.md`. |
| `services/intelligence.py` | Aura backend client — `send_conversation_metrics()` (session-end conversation metrics, the LiveKit counterpart of the ElevenLabs post-call webhook). The LLM does **not** route through this client — it uses the OpenAI-compatible endpoint via the stock plugin. |
| `services/experiment.py` | Backend experiment-service client — `ExperimentService.assign()` does one batch per-session A/B assignment at session start (gated by `AGENT_EXPERIMENTS_ENABLED`; fails open). Result is stored on `SessionConfig.experiments`. Mirrors IntelligenceService's HTTP style. The agent only declares names + obeys the backend's verdict; bucketing is server-side. **Dormant scaffold — no active consumer:** the `aiTTSProvider` experiment (which routed the session TTS provider) was retired, so `SessionResolver._resolve_experiments()` still assigns + stores when enabled but nothing reads the result today. A future experiment adds its own consumer that reads `SessionConfig.experiments`. |
| `metrics/` | `session_metrics.py` (`SessionMetrics`) — accumulates per-session LiveKit usage (agent-turn count + STT/TTS audio) and POSTs the conversation-level totals to Aura on shutdown. Per-turn dialogue metrics aren't collected (the OpenAI endpoint owns dialogue ids). |
| `config/` | Typed-dataclass config, one class per file; `app.py` = composite `Config` + `get_config()`. |
| `logger.py` · `context.py` · `errors.py` | Top-level cross-cutting modules (Aura convention), next to `main.py`. `Context` is a pure correlation value object (ids only); the LiveKit `JobContext` is passed explicitly to the collaborators that need it. `logger.py` is the `setup_logging` facade: it applies `LOGGER_LEVEL` and wires the `log/` package below. |
| `warmup.py` | Process warm-up, run from `prewarm()` in the idle job process: imports the modules the first turn would otherwise load lazily (`openai.resources` — the SDK pulls every resource, admin types included, on the first `client.responses` access — and the Cloud Logging handler's `google.cloud.logging*`), force-builds the pydantic schemas behind the response stream (`openai.types.responses` / `chat` / `shared`; the SDK defers every model build to first use), builds the SDK's cached stream-event adapter, and imports `livekit.agents.llm.async_toolset` (lazily imported by `AgentActivity.start`) and `anyio._backends._asyncio` (imported on httpcore's first request, which also resolves anyio's lazy stream/socket submodules). It ends by collecting and calling `gc.freeze()`, so later full collections skip the ~270k startup objects: unfrozen, those collections cost ~100 ms mid-session. That is why `warm_process()` runs last in `prewarm()`, after the VAD load. Best-effort — each step is counted, never raised — and the `WarmupReport` is stashed in `proc.userdata["warmup"]` so the entrypoint's `Session starting` row carries `warmup_*` fields; `warmup_failures > 0` means a turn is paying that cost again. Motivated by the 1.8.1 loop-stall monitor's first session (404 / 668 / 202 ms stalls, all first-use costs). |
| `log/` | Logging support behind `logger.py`, one module per concern: `log_levels.py` (the custom `audit` level), `gcp_logging.py` (the Cloud Logging forwarder) and the nine vendor screens — `eot_logging.py` (`EotDiagnosticsFilter` — unlocks the runtime's per-turn end-of-turn verdict without raising all of `livekit.agents` to DEBUG), `redact_logging.py` (`SpokenTextRedactionFilter` — elides spoken content the runtime logs on its own, e.g. the text embedded in a TTS zero-audio error), `tts_logging.py` (`TtsStreamFailureFilter` — codes a mid-utterance TTS socket close as `TTS_STREAM_CLOSED` and downgrades its duplicated `asyncio` echo so one incident counts once), `stt_logging.py` (`SttStreamClosedFilter` — codes a LiveKit Inference STT socket drop as `STT_STREAM_CLOSED` and demotes the SDK's duplicate `Error in recv_task` ERROR traceback, since the runtime retries and recovers), `llm_logging.py` (`LlmInferenceTracebackFilter` — demotes the SDK's duplicate `Error in _llm_inference_task` traceback for an LLM failure the session already reports, coding a provider content-filter refusal as `LLM_RESPONSE_FILTERED`), `transport_logging.py`, `deprecation_logging.py`, `recorder_logging.py` and `telemetry_logging.py` (see the `logging` rule). `log_screening.py` is their shared substrate — `screened_message()` / `record_template()`, the two ways to read a vendor message, plus `demote_to_debug()`, the only sanctioned way to lower a level (its mark is what stops `eot_logging.py`'s allow-list dropping a deliberately demoted row on a later handler); no screen reads `record.msg` directly or sets `levelno` by hand, and `test/unit/test_log_screen_conformance.py` holds the registry every screen must appear in. Each screen names its logger with a literal (`logging.getLogger("eot_logging")`), not `__name__` — that name is the `component` field in Cloud Logging, so it must survive a move. The package is `log/`, not `logging/`: `python src/main.py` puts `src/` on `sys.path`, so a `src/logging` package would shadow the standard library in every worker and job process. |
| `utils/` | one helper per file: `redact.py` (PII), `room_parser.py` (room/metadata parsing), `is_uuid.py`, `sdk_versions.py` (the installed SDK versions logged per session). |

## Data flow

```
User audio → Deepgram STT → session LLM → [Aura /ai/openai/chat/completions] → TTS provider → LiveKit room
                                                          ↓
                          SessionMetrics (LiveKit usage totals, on session end) → Aura /ai/conversations/{id}/metrics
```

On session end the agent also POSTs conversation-level totals (duration, agentTurns, stt/tts audio)
to Aura `/ai/conversations/{id}/metrics` — the LiveKit counterpart of the ElevenLabs post-call
webhook.

### The agent never sees IntelligenceService's dialogue id

Anything that wants to hand the app a dialogue id (or the saved reply) from the agent has to
get it onto the wire first. Today nothing carries it:

- **Streamed events carry OpenAI's id, not ours.** IntelligenceService creates the dialogue id
  itself (`getDialogueIds` in `chatResponse.js`) and uses it only for logging and the saved row.
  On the streaming path the events are OpenAI's own, with OpenAI's `resp_…` id; the
  `resp_<dialogueId>` form appears only in the non-streaming response, and the plugin always streams.
- **A custom SSE event is dropped before `llm_node`.** The stock plugin's `_parse_event`
  (`livekit/plugins/openai/responses/llm.py`) handles seven event types (`error`,
  `response.created`, `response.output_item.done`, `response.output_text.delta`,
  `response.completed`, `response.failed`, `response.incomplete`) and returns `None` for
  anything else, so no `ChatChunk` is built.
- **`X-Dialogue-ID` is not sent on the routes the agent calls.** IntelligenceService sets it on
  `/ai/dialogue/ask`, `/ai/dialogue/say` and onboarding `ask` only, not on `/ai/openai/responses`
  or `/ai/openai/chat/completions`. Reading it would also need a custom `httpx` client with a
  response hook, matched to the right generation.

**Why:** answering "can `agent_reply_saved` carry the dialogue id?" in a PR review took a full
trace through both repos; these are the three facts that trace turned up.

## Config resolution priority

1. Job metadata (LiveKit server dispatch) → 2. Environment (`.env`). The participant identity is only the `user_id` fallback.

## Entry points run in separate processes

`main.py` runs in the worker; `entrypoint.py` runs per job (subprocess). Cross-cutting setup
(e.g. `setup_logging`) is re-asserted in the entrypoint after LiveKit's own setup.
