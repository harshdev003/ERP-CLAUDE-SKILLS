# report-bugsnag-errors

Proactive error **digest** across the 12 `aura-health` Bugsnag projects. Read-only against the [Data Access API v2](https://developer.smartbear.com/bugsnag/docs/data-access).

## Goal

Answer *"what's new or getting worse across web + mobile?"* in one command, without opening Bugsnag project by project. This is the proactive complement to [`eng:investigate-bugsnag-errors`](../investigate-bugsnag-errors/SKILL.md), which is the reactive "drill into this one error" side. Every error row in the digest ends with the exact `investigate bugsnag --error <id>` command, so the two chain.

## Inputs

All optional — sensible defaults when the user is vague:

| Flag | Default | Meaning |
|---|---|---|
| `--all-projects` | on (when `--project` omitted) | Digest across all 12 projects |
| `--project <slug>` | — | Limit to one project (fuzzy match, so `userweb` → `aura-userweb`) |
| `--since <dur>` | `7d` | Window as Bugsnag duration shorthand: `1h`, `24h`, `7d`, `30d`. Daily digest = `24h` |
| `--limit <n>` | `10` | Cap each section (new / top) at N rows |
| `--release <spec>` | — | Scope to an app version: `1.29.0` for that version alone, or `>=1.28.0` for it and everything released after it. Needs `--project` and `--release-mode` |
| `--release-mode <mode>` | **none — always explicit** | `seen-in` (the error occurred on that version) or `introduced-in` (it first appeared there) |
| `--slack` | off | Emit a Slack mrkdwn payload (JSON) for `#alerts-bugsnag` instead of the chat digest |

## Run the query

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/skills/report-bugsnag-errors/scripts/report.py <flags>
```

Pass the digest through to the user verbatim. The final line is a drill-in hint into `eng:investigate-bugsnag-errors`.

## Digest sections (stable contract)

1. **Headline rollup** — error signatures / events / users for the window, split **Web vs Mobile vs Desktop/embed** via app-family routing, plus a total line.
2. **🆕 New error classes** — errors whose *true* first occurrence is inside the window (see the `first_seen_unfiltered` note below), newest first.
3. **Top errors by event count** — the loudest signatures across the scope, each with a `→ Drill in: investigate bugsnag --error <id>` hint.
4. **Per-project breakdown** — signatures / events / users per project, grouped by app family, sorted by event volume.

0-result scopes print a "0 errors active in `<scope>` since `<since>`" line rather than erroring.

## Slack delivery (`--slack`)

Same Python-prepares / Claude-posts split as the investigate skill's Slack action — **never auto-posted**:

1. `report.py --slack ...` prints a JSON payload: `{"channel_suggestion": "#alerts-bugsnag", "text": "<Slack mrkdwn digest + footer>"}`. The script only *emits* the payload — it does not post. It can't read AI Knowledge, so it names the channel only.
2. **Resolve the canonical `#alerts-bugsnag` channel ID from `Tools/Slack`** (already in `knowledge.reads`) — don't rely on name resolution. This matches the eng report-skill convention (e.g. `#eng-budget` → `C05PC18APLH`, canonical ID in `Tools/Slack`). Show the user the draft + confirm the channel before posting; **never auto-post**.
3. On confirmation, **invoke [`shared:post-to-slack`](../../../shared/skills/post-to-slack/SKILL.md)** with the payload text and that channel ID; that skill owns the connection (MCP-first, `SLACK_BOT_TOKEN` script fallback) and the unfurl-off default — don't call Slack directly here.

The payload text is a compact glanceable summary (headline + top new + top by events), not the full chat digest, and already ends with the canonical footer `_Generated by `eng:report-bugsnag-errors:<version>`_` (`format.py` stamps `:<version>` from `metadata.version` at runtime) per `Tools/Slack` → Post format, so don't have the slack skill add a second. Stamp the date at post time.

## Release scoping

Monitoring baselines on the latest release, so a digest that mixes every version
ranks by whatever accumulated on versions nobody is shipping fixes for. Measured
on `ai-aurie-ios` over 30d: **49,762 events across 100 signatures unscoped, 166
across 43 on 1.29.0 alone.** Scoping is not a refinement of that number; it is a
different number.

```bash
--project ai-aurie-ios --release 1.29.0    --release-mode seen-in        # this version
--project ai-aurie-ios --release '>=1.28.0' --release-mode seen-in       # and everything after
--project ai-aurie-ios --release 1.29.0    --release-mode introduced-in  # regressions
```

Four things the flags deliberately refuse to guess:

- **`--release-mode` has no default.** `seen-in` and `introduced-in` answer
  different questions and return different sets (43 vs 25 on 1.29.0/30d).
  Picking one silently is how the next wrong table gets produced, so omitting it
  is an error rather than a default.
- **`--release` requires `--project`.** A version string means different things
  in different projects — 1.29.0 of the iOS app is not 1.29.0 of UserWeb — so an
  org-wide scoped digest would silently mix them.
- **A version with no release record is an error**, listing the known versions.
  It would otherwise render as a clean, empty, entirely plausible digest.
- **`>=` means "this version and everything released after it"**, resolved from
  the releases endpoint in release-time order — not by comparing version
  strings. A hotfix cut from an old branch belongs in the answer even though its
  version string sorts low.

**The output always states the scope it used**, including the TestFlight caveat
below. A release-scoped digest that does not say so is the failure this exists to
prevent — the numbers look like the project's rather than the version's.

Why `>=` is N requests rather than one query, and why an unknown filter key is
never sent: see [Tools/Bugsnag](https://www.notion.so/35a75e23af2081b1a021d7b2b8999e2f)
→ Filtering (canonical). The short version is that Bugsnag has no range and no
OR on the version fields, and ignores an unknown filter key rather than
rejecting it.

## Caveats

- **"New" uses `first_seen_unfiltered`.** Bugsnag's plain `first_seen` is *clamped to the query window* — a 7-day query reports `first_seen` as 7-days-ago even for an error that's months old, so it would flag every active error as new. The skill uses `first_seen_unfiltered` (the true first occurrence) to detect genuinely new errors.
- **Per-project cap.** The fan-out fetches the top 100 signatures *by event volume* per project (one page each). A brand-new but very-low-volume error outside the top 100 of a high-traffic project can be missed — narrow with `--project` or a shorter `--since` for a focused new-error sweep.
- **`users` is a Σ across signatures** (an upper bound — the same user hitting two errors counts twice). Treat it as a rough volume signal; `events` is exact.
- **TestFlight cannot be separated from the App Store.** `ai-aurie-ios` emits only `production` and `development`, and TestFlight builds report `production`. A digest scoped to a version released in the last two weeks is TestFlight-weighted; the output says so rather than letting a reader assume store traffic.
- **A multi-version scope costs one request per version** and sums `events` per error (an event belongs to exactly one version, so they partition cleanly). `users` is the **max** across versions, not the sum, and is a lower bound — separate queries cannot tell one person on two versions from two people.
- **Cross-project fan-out is sequential** (one API call per project) and skips any project that rate-limits or fails transiently, same as cross-project triage — a flaky project never kills the run.

## PII guardrail

Read-only, same posture as the investigate skill's triage/focus modes: the digest shows only extracted error-signature fields (class, message, counts, timestamps, project). It never echoes `request` / `user` / `device` / `metadata` blocks. Aurie projects (`ai-aurie-ios`, `ai-aurie-macos`, `aiweb`) carry user-conversation text in metadata, but the digest never reaches into it.

## Setup (one-time, per user)

1. **Bugsnag personal auth token** — self-serve at <https://app.bugsnag.com/settings/my-account/auth-tokens> → Personal auth tokens.
2. **Store it** as `BUGSNAG_TOKEN` under the `env` block in `~/.claude/settings.json`. Restart Claude Code.
3. **Python deps** — `python3 -m pip install --user -r ${CLAUDE_PLUGIN_ROOT}/skills/report-bugsnag-errors/scripts/requirements.txt`. Just `requests`.

There is **no MCP fallback** for Bugsnag, so a missing `BUGSNAG_TOKEN` is a hard fail with a clear "create a token + add to settings + restart" message.

**Cowork caveat ([PROD-1305](https://linear.app/aura-health/issue/PROD-1305)):** `mcp__workspace__bash` strips host env. Inside Cowork, paste-export `BUGSNAG_TOKEN` once at session start:

```bash
export BUGSNAG_TOKEN='<paste from host ~/.claude/settings.json>'
```

## Scheduling

The skill is on-demand, like the other `eng:report-*` skills. To run it on a cadence (e.g. a Monday `#alerts-bugsnag` digest), wire it through the scheduling skill / a cron — out of scope here.

## Edge cases

- **0 errors in the scope + window** → prints "0 errors active in `<scope>` since `<since>`" with a suggestion to widen `--since`. Doesn't error out.
- **Auth fails (401)** → the API client prints the specific failure with the one-line fix (regenerate token, add to settings, restart), not an opaque traceback.
- **Project slug typo** → fuzzy-match against the live project list; if no single match, the available slugs are listed.
- **A project rate-limits (429) during the fan-out** → handled inside the API client (5 retries with `Retry-After`); per-project failures are skipped rather than failing the whole run.
- **Re-running the same digest** → safe (read-only); no idempotency concern.
