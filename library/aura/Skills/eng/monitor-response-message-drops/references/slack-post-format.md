# `--post`: one Slack message per drop

`monitor.py --post` reports each new drop on the monitored version to
`#ai-conversation-message-drops` (`SLACK_CHANNEL` in the script — private, owned by Jerome).
That channel is the **only** place the dropped text goes. Cards, other channels and the
terminal readout carry counts, sizes and response ids; the text stays in OpenAI and here.
The decision to put the text and the user id in this one channel was made by the channel
owner on 2026-09-04 and is recorded on [ENG-1246](https://linear.app/aura-health/issue/ENG-1246).

## The message

Mirrors the k8bot `*CONVERSATION RATED*` shape the team already reads in `#ai-data-intelligence`,
so the bracket line is greppable the same way.

```
*MESSAGE DROPPED*
:repeat: *Paraphrase* — the dropped item restates the kept reply's points in different words; nothing new lost.
_<optional operator note>_
2026-09-04 22:09:00Z · kept 826 chars · dropped 704 chars · <https://platform.openai.com/logs/resp_…|OpenAI log>

*User turn* _(summary of 881 chars)_
<code block: verbatim text, or the operator's summary when the original is over 600 chars>

*Assistant — kept (delivered)*
<code block>

*Assistant — dropped*
<code block>

`[dialogue: <dialogueId>, conversation: <conversationId>, user: <uid>, prompt:<name>:<version>, model: <resolved model>]`

_Generated by `eng:monitor-response-message-drops:<version>` · <date> · <runner> · prod_
```

The bracket values come from the stored response's `metadata` (IntelligenceService stamps
`dialogueId`, `conversationId`, `user`, `name`, `version`) and its `model` field (the model
OpenAI actually served, e.g. the concrete `chat-latest` snapshot). The user turn is the
newest `role: user` item in `GET /v1/responses/{id}/input_items`. Drops are posted
**oldest first**, one message each, no thread — the thread is left for discussion.

### Categories

| verdict | emoji | who decides | meaning |
|---|---|---|---|
| `repeat` | :repeat_one: | script | byte-equal (or trivially so) to the kept reply |
| `opener` | :wave: | script | short greeting / presence line, matched by the opener regex |
| `paraphrase` | :repeat: | operator | same points reworded; often the same closing line |
| `sign-off` | :checkered_flag: | operator | a one-line closer after a complete reply |
| `continuation` | :warning: | operator | a point, question or turn the kept reply does not contain — the real cost |

The script posts `repeat` and `opener` on its own. Anything the classifier labels `read` is
**held** until a verdict arrives in the verdicts file. A filed verdict also overrides a
feature verdict (an item the regex calls an opener that is really a sign-off, say).

## The verdicts file

A JSON object keyed by `responseId`, passed as `--verdicts <path>`:

```json
{
  "resp_0087da92a4750777006a9b4177109087d1a74567d9e7959519": {
    "verdict": "paraphrase",
    "note": "Safety-adjacent turn: the kept reply already carries the acknowledgement.",
    "summaries": {
      "user": "…2–4 sentence summary of the user turn…",
      "kept": "…summary of the delivered reply…",
      "dropped": "…summary of the dropped item…"
    }
  }
}
```

- `verdict` — required; one of the five categories above.
- `note` — optional; one line, rendered in italics under the category. Use it for context a
  reviewer needs (a safety-adjacent turn, a second drop in the same conversation).
- `summaries` — required for **each** of `user` / `kept` / `dropped` whose text is longer
  than `LONG_TEXT_CHARS` (600). Shorter texts post verbatim and ignore any summary given.
  The script never summarizes on its own: a drop with a missing summary is held and says
  which key it needs. Summaries carry no names, no locations, no quoted lines.

Write the file anywhere outside the repo (the scratchpad is the usual place); it is
per-run input, not state. Anything in it for an already-posted id is ignored.

## Dedup and state

Posted ids live in the per-version state file (`<state-dir>/<version>.json` → `posted`),
carried forward on every tick. Overlapping `--since` windows therefore never post a drop
twice, and a Slack failure leaves the id unposted so the next tick retries it.
`--post` refuses `--no-state` for this reason. `--post-dry-run` renders every message
that *would* post and records nothing.

the monitoring card, because it is the one outcome that changes the decision.
