# Regenerating `Guide/Index` (Step 7b)

`Guide/Index` is the flat Path → Description map `search-knowledge` and `retrieve-knowledge` route against. It is a generated artefact — the one page in L4 that is safe to overwrite wholesale.

It is a routing aid, not a content mirror — keep entries terse.

Whether to regenerate is decided by the two state checks in the skill body's Step 7b (staleness, then tree drift). Both are questions about the live tree, not about what this run wrote. The steps below are the regeneration itself, once one of those checks has fired.

1. Resolve `Guide/Index` (child of `Guide`). If it doesn't exist, present the proposed creation in chat (same plan-first discipline as the parent indexes for Harvest/Health Check) and create it on approval.
2. **Walk the tree with the script, not by hand:**

   ```bash
   python3 ${CLAUDE_PLUGIN_ROOT}/skills/harvest-knowledge/scripts/walk_tree.py \
     --sections /tmp/sections.json --out /tmp/guide-index-walk.json --live-count <paths on the live page>
   ```

   `sections.json` is the `{section title: page id}` map from [about-sections.md](about-sections.md). The script walks every section to the leaves and **opens every block that has children**: toggles, columns, callouts, synced blocks, list items, quotes. A child page can sit inside any of them, and then its parent is a block, not a page. A walk that follows only `child_page` blocks drops it with nothing to signal it: run 2026-11-15-run1 lost 19 live pages this way (475 → 455 paths). Content also nests three or more pages deep (`Tools/Aura API/Users/Get User By Id`). Each entry carries its path, id, kind (page or database), the URL the API returns, and whether it sat inside a block. **One entry per page id:** a page with no title is kept as `(untitled)`, and its children are walked under that path; two pages sharing a title under one parent are both kept and flagged `duplicate_path`, because a path alone can't tell them apart. So the count is the real number of pages and databases, which is what the collapse guard compares with the live index. **Exclusions** (applied by the script): `Guide/Harvest` and `Guide/Health Check` with their subtrees (operational audit logs), dated `Signals/<topic>` snapshot pages (the parent Signals page lists them; the date can be anywhere in the title, as in `<Producer> — YYYY-MM-DD snapshot`), the section roots themselves, and `Guide/Index`.
3. For each page/database, keep its **URL** alongside the path — the path is rendered as a link to the page, not as bare text (step 5). Then derive a one-sentence description:
   - First, take the `**At a glance:**` opener if present.
   - Otherwise, take the first sentence of the page body.
   - For databases, use the parent page's description of what the DB contains.
   - Truncate to ~140 chars; strip Markdown formatting.
4. Group entries by top-level section. Within a section, keep alphabetical order by full path.
5. Render the page body as:

   ```markdown
   **At a glance:** Path → Description map of every page and database in AI Knowledge. Regenerated by `harvest-knowledge` on every `apply` run. Used by `search-knowledge` and `retrieve-knowledge` as a discovery / routing aid.

   _Last regenerated: <YYYY-MM-DD> by harvest run [<run page>](<url>)._

   # Identity
   - [`Identity/Audience`](<url>) — vertical taxonomy and ICP definitions.
   - …

   # Products
   - [`Products/Aurie`](<url>) — Aurie's brand voice, tone, and product principles.
   - [`Products/Aurie/Subscription`](<url>) — SKUs, trials, grace window.
   - …

   # Domain
   - [`Domain/Competitors`](<url>) — competitive landscape snapshots.
   - …

   # Procedures
   - …

   # Tools
   - …

   # Learnings
   - [`Learnings/Experiments`](<url>) — A/B tests run on Aurie (database).
   - …

   # Signals
   - [`Signals/Conversation Patterns`](<url>) — one write-once row per rating.
   - …

   # Sources
   - Native to this teamspace (automated index; regenerated by `harvest-knowledge`).
   ```

6. **Check the walk did not collapse, before writing anything.** `walk_tree.py --live-count` does this: it exits `3` and writes nothing when no section resolved, or when the walk found fewer paths than the live page by more than max(3, 2%). Abort the regeneration then, leaving the existing page untouched. The margin is deliberately small: the 19-page loss above was 4%. `--allow-shrink` is for a teamspace that really did shrink, decided by a person after reading the removed paths. Same rule the About resolution uses in [about-sections.md](about-sections.md): a collapsed walk and a real restructure look identical in the output, so treat a sharp drop as the failure. Step 7 runs only once this passes.

7. Replace the page body in full via `notion-update-page` (this is the one page in L4 that's safe to overwrite wholesale because it's a generated artefact). Record the regeneration as a one-line entry on the run page under "Edits applied this run › Pre-review" with edit type `regenerated Guide/Index`, including the added/removed path counts.

## Every path is a link, not bare text

The `[`path`](url)` form renders as a linked code span — `rich_text()` parses link and code together, so the path keeps its monospace styling and becomes clickable. A bare `` `path` `` costs more than aesthetics, which is why the link is not optional:

- **`healthcheck-knowledge`'s orphan detector (#3) reads inbound hyperlinks**, and a plain-text path is not one. The index references nearly every page in the teamspace, so when its bullets carry no href it contributes no inbound link to any of them and almost everything reads as orphaned. Measured on the 2026-09-03 run: 0 of 155 bullets linked, 17 correctly-indexed pages in the orphan report.
- **Notion's own backlinks panel stays empty**, so a reader on a content page cannot see that the index references it.
- **A path that has drifted is indistinguishable from one that has not.** A link 404s when its target is archived or deleted; bare text just sits there reading correctly.

Carry the URL through step 2's walk rather than reconstructing it from the page id afterwards — the API returns it on the page object, and a hand-built URL silently misses the workspace-domain and slug forms Notion actually serves.

## Reading the index back: parse the code span, not the text before the dash

The tree-drift check compares the walked path set against the paths the live page lists, so it has to read each bullet back. Take the path from the **backticked code span** — the `rich_text` run carrying the `code` annotation — and never by splitting the bullet on its first `—`.

Paths contain em-dashes. `Procedures/Engineering/Monthly Tasks/Coach Payout — Step by Step` is a real path, and a first-dash split truncates it to `Procedures/Engineering/Monthly Tasks/Coach Payout`, which then matches nothing in the walk. The truncated entry is reported as present-in-index-but-absent-from-tree **and** its untruncated twin as present-in-tree-but-absent-from-index, so one path yields two spurious differences.

Measured cost: **28 reported differences on a tree whose real drift was zero.** Every one traced to a path containing a dash. A check that over-reports this way triggers a wholesale regeneration of a correct page, which is the one page in L4 that is overwritten in full.

## Why step 6 guards step 7

The page is overwritten wholesale, so a walk that resolved two sections instead of nine would replace a full index with a short one and report success. Nothing downstream can tell that apart from a teamspace that genuinely shrank — `search-knowledge` simply stops finding the paths that fell out.

**Every regeneration is also a full-tree walk.** Reusing the previous page's path list and adding to it carries forward any path an earlier walk missed, and a missing path is invisible in the output — the page still renders as a complete index.
