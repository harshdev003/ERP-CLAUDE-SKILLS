# Search Knowledge

Discovery layer for the AI Knowledge teamspace. Turns a free-form question into a ranked list of candidate paths, so the caller (a user in chat, or another skill) can decide what to fetch next via `retrieve-knowledge`.

**Scope today:** Notion AI Knowledge teamspace (`34975e23-af20-8110-89ec-004231809285`).
**Not in scope:** fetching page content (see `retrieve-knowledge`), writing (see `record-knowledge` / `ingest-knowledge` / `harvest-knowledge`).

## Core contract

- **Paths, not content.** The skill returns `{ path, title, description, url, score, source }` records. Callers fetch the body separately via `retrieve-knowledge` if they want it.
- **Index first, search second.** The `Guide/Index` page is the cheap, curated routing aid. Only fall back to `notion-search` when the index produces no usable hit.
- **Stateless and read-only.** No writes, no audit trail, no plan/approval flow.
- **Always teamspace-scoped.** Every `notion-search` call passes `teamspace_id=34975e23-af20-8110-89ec-004231809285`. Never spill into other workspaces.
- **MCP-first, REST fallback.** Per the repo convention ([CLAUDE.md → Tokens are soft requirements](../../../../CLAUDE.md#tokens-are-soft-requirements)) this skill prefers the Notion MCP (`notion-search`). When the MCP is unreachable but `NOTION_TOKEN` is set — a host session without the connector loaded, or a dropped connector — fall back to the bundled [`scripts/notion_rest.py`](scripts/notion_rest.py) helper (see Step 3). Inside Cowork sandboxes the token is stripped ([PROD-1305](https://linear.app/aura-health/issue/PROD-1305)); if neither path is available, say so plainly rather than returning nothing silently.
- **Honest about gaps.** If neither stage finds anything, say so plainly and suggest the closest section the user could browse — don't synthesise content.

---

## Inputs

- `query` (required) — free-form natural-language question or topic.
- `limit` (optional, default `5`) — max candidate paths to return.
- `section` (optional) — restrict results to a top-level subtree (e.g. `Learnings`, `Identity`, `Signals`).
- `deep=true|false` (optional, default `false`) — when `true`, run the Notion search fallback even if the index returned hits, and merge results. Use sparingly; the index alone is usually enough.

---

## Step 1: Resolve the index

`Guide/Index` is the canonical Path → Description map. It's regenerated by `harvest-knowledge` on every sweep, and drift is flagged by `healthcheck-knowledge`.

1. Fetch the About page (one hardcoded ID, shared with the other knowledge skills):

   ```
   AI_KNOWLEDGE_ABOUT_PAGE = "9ee75e23af20830aa49101a40466a789"
   ```

2. From About, follow the link to `Guide`, then to its `Index` child page. Cache the resolved page ID for the rest of this session.
3. Invoke `shared:retrieve-knowledge` with `path=Guide/Index` to pull the body. This rides the local 24h cache (see [`retrieve-knowledge/references/cache.md`](../retrieve-knowledge/references/cache.md)) — first call of the day refetches, subsequent calls serve from disk. Parse the returned body as a list of entries; each is one line of `path — description` (grouped under section headings — Identity, Products, Domain, Procedures, Tools, Learnings, Signals, etc.). Keep the section header so a `section=` filter can apply. (Direct `notion-fetch(<index-page-id>)` is acceptable as a fallback if the cache layer is unavailable, but prefer the cached path.)

If the Index page doesn't exist yet (early adopters running this skill before the first post-ENG-413 harvest), skip Step 2 and go straight to the search fallback in Step 3 — note in the response that the index is missing so the user can run `harvest-knowledge` to seed it.

---

## Step 2: Score the index against the query

For each index entry, compute a relevance score against `query`:

- **Strong match** — query terms appear in the path's last segment or in the description's first clause.
- **Weak match** — query terms appear anywhere in the description.
- **No match** — drop.

Tiebreak by section preference if the query implies one (e.g. "what did we learn about…" prefers `Learnings/`, "how do users feel about…" prefers `Signals/`). If `section=` is set, drop entries outside that subtree.

Take the top `limit` hits. If the best score is below a confidence floor (e.g. only weak matches), proceed to Step 3 to augment with search results.

---

## Step 3: Notion search fallback

Trigger when:
- Step 2 returned zero hits, or
- Step 2's best hit was a weak match, or
- The caller passed `deep=true`.

Run a teamspace-scoped Notion search:

```
notion-search(
  query=<query>,
  teamspace_id="34975e23-af20-8110-89ec-004231809285",
  filters={}
)
```

**When the MCP is unavailable** (no connector, or it errored) but `NOTION_TOKEN` is set, run the same search through the bundled helper instead:

```python
from notion_rest import notion, MCPFallback  # scripts/notion_rest.py

if notion.available:
    # REST /search can't scope by teamspace_id server-side (only the MCP can),
    # so over-fetch and post-filter by ancestry: keep a hit only if its parent
    # chain (notion.root_page_of) resolves into the AI Knowledge teamspace.
    raw = notion.search(query=<query>, page_size=100)
    hits = [h for h in raw if in_ai_knowledge_teamspace(h, notion)]
else:
    raise MCPFallback("no Notion MCP and no NOTION_TOKEN — report the gap")
```

The MCP path is preferred when available because it scopes by `teamspace_id` server-side; the REST `search` matches everything the integration can see, so the teamspace post-filter is mandatory to honour the "never spill into other workspaces" contract above.

For each hit, derive its path by walking parent links (use the same About → section mapping `retrieve-knowledge` uses). Add to the candidate list with `source=search` and a synthesized one-line description from the page's `**At a glance:**` opener if present, or its title otherwise.

Merge with Step 2 results, dedupe by path (prefer the index entry's description — it's curated), re-sort by score, truncate to `limit`.

---

## Step 4: Return

Hand back a structured list. Keep it terse — this skill is a router, not a renderer.

```
[
  {
    "path": "Learnings/Experiments",
    "title": "Experiments",
    "description": "A/B tests run on Aurie — hypothesis, variant, outcome, learning.",
    "url": "https://www.notion.so/...",
    "score": 0.92,
    "source": "index"   // or "search"
  },
  …
]
```

Always include a one-line follow-up suggestion in the chat message: "Use `retrieve-knowledge path=<top hit>` to read the full content." If the top hit is a database (`Learnings/*`), suggest filters the caller might want to pass.

If nothing matched, return an empty list and a chat message naming the section closest to the query so the user can browse from there.

## Out of scope

- **Fetching page content** → `retrieve-knowledge`
- **Writing a new page** → `ingest-knowledge` (single source) or `record-knowledge` (Learnings/Signals row)
- **Periodic upstream sync (which regenerates the index)** → `harvest-knowledge`
- **Auditing the teamspace (which flags index drift)** → `healthcheck-knowledge`

---

## Relationship to other knowledge skills

| Skill | Shape |
|---|---|
| `search-knowledge` | Free-form query → ranked list of paths (this skill) |
| `retrieve-knowledge` | Known path or query → content |
| `ingest-knowledge` | On-demand single source → writes L4 |
| `harvest-knowledge` | Periodic upstream → L4 sync; **regenerates `Guide/Index`** |
| `healthcheck-knowledge` | Periodic L4 audit; **flags index drift** |
| `record-knowledge` | Structured write to Learnings / Signals databases |

The natural flow when a user asks an open-ended knowledge question is: `search-knowledge` to find the path, `retrieve-knowledge` to read it.
