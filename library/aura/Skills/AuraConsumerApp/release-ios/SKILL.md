# Release iOS

## Goal

Get a version onto TestFlight **and** onto `main` as a tag and a published GitHub
release, in an order where a failed build never leaves a stranded version bump.

Two halves, split across two tools deliberately:

| | Owner | Why |
|---|---|---|
| Switch env, bump, archive, sign, upload, Bugsnag dSYM | **fastlane** (`fastlane/Fastfile`) | It already does this correctly and is the thing release engineers test |
| PR, merge, tag, GitHub release | **this skill** | All git-history operations on a protected branch — fastlane cannot push to `main`, and a tag placed on a local bump commit points at a commit that squash-merge replaces |

**The Fastfile no longer tags.** The `tag` lane was deleted and the `release` lane's
tag and Slack steps removed when this skill landed.

### That split is not theoretical here

The old `tag` lane committed `project.yml`, tagged the **local** bump commit, and
pushed. The squash merge then created a *different* commit on `main`, so the tag was
left pointing at a commit that never landed:

```
v1.29.0-1  →  ef71c27c3  "Release v1.29.0 (build 1)"   NOT an ancestor of main
v1.28.0-1  →  (same shape)                             NOT an ancestor of main
```

`step_tag` refuses to create a tag that is not an ancestor of `origin/main`, which is
exactly the case the old lane produced.

## Inputs

- **env** — `dev` or `prod`. Required. Selects `dev:true` on the lane, which runs
  `make env-<env> release` and points the archive at that env's Firebase + API.
- **version + build** — explicit: `--version 1.30.0 --build 1`.
- **or level** — `--level major|minor|patch|build`. `major`/`minor`/`patch` bump the
  version and **reset the build to 1**; `build` holds the version and increments the
  build, which is how you re-ship a version whose binary was rejected or superseded.

The baseline is read from **`origin/main`'s** `project.yml`, not the working tree, so
a stale checkout cannot propose a version below what shipped.

## Ordering — and the guard that makes it safe

```
branch → bump → commit → ARCHIVE + UPLOAD → push branch → PR → squash-merge → tag → gh release
                         └──────────────┘
                       build happens BEFORE the PR
```

Building first means a failed archive costs a local branch and nothing else — no
version bump sits merged on `main` for a release that never shipped.

The cost is that **the tagged commit is not the built commit**: a squash merge creates
a new one. The script closes that gap with two checks, and neither is optional:

1. **Before merging** — re-fetch and confirm `origin/main` has not moved since the
   branch was cut. If it has, the squash-merge commit would carry a different tree
   than the binary on TestFlight. Stops, and tells you to cut a new build.
2. **After merging, before tagging** — confirm the merge commit's tree is
   byte-identical to the archived commit's tree, and that the merged commit really
   declares the version being tagged.

`--allow-drift` overrides both. It means "tag a commit that was never built" — only
reach for it when you have looked at the diff and know why it is immaterial.

## The version lives in `project.yml`

The `.xcodeproj` is **generated by xcodegen and gitignored**, so the version's source
of truth is `project.yml` — and it appears **three times**, once per target:

| Target | Keys |
|---|---|
| `AuraConsumerApp` | `MARKETING_VERSION`, `CURRENT_PROJECT_VERSION` |
| `AurieWidget` | the same two |
| `IterableNotificationServiceExtension` | the same two |

All must agree or App Store Connect rejects the upload. `read_version_at` reads every
target and **refuses to proceed if they diverge**, rather than picking the app's and
shipping a mismatched extension.

The bump is delegated to the **`updateVersion` lane**, not reimplemented here. Three
reasons, and the third is the load-bearing one:

- One writer for `project.yml`, so the skill and the lane cannot drift apart.
- `updateVersion` also runs `make proj`, which the archive needs anyway.
- The `release` lane calls `updateVersion` again with the same values. Because it is
  the *same code path*, the second write is byte-identical and leaves the tree clean —
  which is what lets `step_build` assert afterwards that the archived tree is exactly
  the commit that will be tagged.

`project.yml` is already in `to_yaml`-normalised form (it carries no comments), so the
lane's YAML round-trip produces a clean four-line diff, not a reformat.

**PyYAML is not in the macOS system Python**, so the skill's own *reads* are a narrow
hand-rolled parse: find the target block by indentation, then require **exactly one**
of each key inside it. Two matches raises rather than guessing — that would mean the
file grew config-specific overrides and the parser needs revisiting.

### `make proj` must not change anything else

`make proj` resolves Swift packages, which can rewrite the tracked
`Package.resolved`. That is a real signal — the archive would use pins the release PR
does not carry — so `step_bump` **stops the run** if anything other than `project.yml`
changed, rather than sweeping it into the bump commit.

## Tag format changed to bare `X.Y.Z-N`

Every tag before this skill carries a `v` prefix (`v1.29.0-1`); 158 of them. This skill
emits **bare** `1.30.0-1`, matching Aura's iOS tags and `eng:release-version`'s backend
tags — one namespace shape across the fleet.

The legacy form is still **recognised, never produced**:

| Where | Behaviour |
|---|---|
| `latest_release_tag` | Accepts both, so the notes range is anchored correctly across the format change instead of treating the first bare tag as having no predecessor |
| `sort_key` | Parses both to the same 4-tuple |
| `untag` lane | Deletes whichever form exists |
| Unfinished-release warning | **Bare only** — see below |

**Legacy tags are deliberately not flagged as unfinished releases.** They have no
GitHub release and never will via this path: `--version X --build N` resolves to the
*bare* tag, so a "resume" against `v1.29.0-1` would cut a fresh build rather than
publish. Warning about all 157 of them with a remedy that does not work is worse than
silence. Back-filling them is a deliberate one-off.

## The GitHub release

Created after the tag is pushed, **on by default**. `--no-github-release` opts out.

There is **1 GitHub release against 158 tags** today (`v1.3.3-1`, Dec 2025) — the
practice never took hold here. This starts it, in the shape `eng:release-version` uses
for every backend repo and the Aura iOS skill uses for Aura:

| | |
|---|---|
| Title | `Release <tag>` — e.g. `Release 1.30.0-1` |
| Body | release-it's default changelog, byte-for-byte: `git log --pretty=format:"* %s (%h)" <last-tag>...<commit>` |
| Mechanic | `--notes-file`, so a long changelog is never an argv problem |

One deliberate delta from the backend shape: **a line above the changelog** naming the
version, build, and the configuration the binary was archived against. `1.30.0-1` alone
does not say whether it was cut against dev or prod Firebase, and nothing else in the
release does.

**`--prerelease` on a dev release.** dev and prod share one tag namespace, so without it
a dev build becomes GitHub's "Latest release" and misrepresents what users are on.

`--verify-tag` is passed on every create. Without it `gh` would invent a tag at the
default branch's tip if the push had silently not landed — a release pointing at a
commit nobody built.

**`--latest=false` when back-filling.** Publishing a tag a later release has already
superseded must not take "Latest" off it. `gh`'s default is *automatic, by date and
version* — genuinely ambiguous for an old version published today — so the script
decides itself: if the newest release tag is not an ancestor of the commit being
published, it passes `--latest=false` and says so.

> **Note:** the release body is git-log-derived and does **not** read `CHANGELOG.md`.
> That is deliberate — one recognisable release body across the fleet beats a per-repo
> improvement on it. `CHANGELOG.md` is still maintained by `eng:update-changelog`.

## Two routes, chosen by `fastlane/.env`

There is one question, and it picks signing **and** upload together:

> Are `APP_STORE_CONNECT_API_KEY`, `APP_STORE_CONNECT_ISSUER_ID` and
> `APP_STORE_CONNECT_KEY_ID` all set?

| | Signing | Upload |
|---|---|---|
| **All three set** | xcodebuild gets `-authenticationKey*`; needs a distribution certificate in the keychain that an installed profile contains | `upload_to_testflight` |
| **None set** | xcodebuild authenticates as the Apple ID **Xcode.app** is signed into; **no certificate needed** | a second `xcodebuild -exportArchive` with `destination: upload` |

Nothing to pass, no flag, nothing to decide. `asc_configured?` in the Fastfile and
`asc_route()` in the pre-flight test the same three variables, so the two halves cannot
disagree and leave a build signed one way and uploaded another.

**A partial configuration is refused**, rather than quietly demoted to the Xcode route.
The demotion would be invisible and the halves fail differently:
`xcode_asc_auth_args` needs all three and would silently drop the API-key flags, so
signing would succeed via Xcode and only the upload would break — well into the build.

### Why the no-key route needs no certificate

`exportArchive` re-signs with a distribution profile, and Apple's **cloud-managed**
distribution certificates — where Apple holds the private key and nothing lands in your
keychain — can only be used by an **Apple ID**. Apple bars App Store Connect API keys
from them at every role, which is what `Cloud signing permission error` reports.

**That is why this is the local default.** Most engineers on this team have the
`CLOUD_MANAGED_APP_DISTRIBUTION` role and *cannot* hold a certificate — the team is also
at Apple's cap of 3 `Apple Distribution` certs, so a new one means revoking a live one.
Being signed in to Xcode is the whole setup.

### Why a second `exportArchive`, not `destination: upload` in gym

The export gym runs must still produce an `.ipa`: gym calls
`ErrorHandler.handle_empty_ipa` when it cannot find one, and xcodebuild is not
documented to leave an `.ipa` behind when it uploads. That would fail the lane **after
the build had shipped** — which inverts the signal this skill depends on. `run` pushes
the release branch only once the upload succeeds and treats a pushed branch as proof of
it, so a lane that ships and *then* reports failure strands a released build with no PR
and no way to re-run: App Store Connect rejects a second upload of the same
version+build.

So gym exports normally — `.ipa` and dSYMs land where the Bugsnag step expects them —
and `upload_via_xcodebuild!` ships that same archive as a discrete step whose failure
cannot be mistaken for a build failure. It costs one extra export, on the local route
only.

### What the no-key route gives up

The transfer happens; the bookkeeping around it does not. `upload_to_testflight`'s
build-processing wait, changelog and tester distribution are all skipped. The build
arrives in TestFlight either way.

### CI must use the key

There is no signed-in Xcode account on a CI runner, so the Xcode route does not exist
there. `uploadTestflight` errors immediately if `ci?` and no key is configured, rather
than discovering it at the upload.

### The 401 pre-flight

The key id, issuer id and `.p8` have to authenticate *together*, and Apple reports any
mismatch as a bare `401` at upload — after the archive. So on the API route, pre-flight
mints the token exactly as spaceship does (`connect_api/token.rb#refresh!`) and calls
`GET /v1/apps?limit=1`. About a second.

- **401 blocks.** The credentials do not work together; the release would have built
  and then failed to upload.
- **403 / offline / no `openssl` warn** instead: the token authenticated, or the check
  could not run, and neither justifies refusing a release.
- **A missing `.p8` file blocks** too.
- **Skipped** on the Xcode route (no token is sent) and when
  `APP_STORE_CONNECT_API_KEY_BASE64` is set (the CI shape, where the lane materializes
  the key itself).

### Why "cert in a profile", not just "cert in the keychain"

On the API route only. If no installed profile contains your certificate, automatic
signing has to mint one — and an App Store Connect API key cannot create cloud-managed
signing assets at any role. The archive succeeds, then export dies with:

```
error: exportArchive Cloud signing permission error
error: exportArchive Provisioning profile "…" doesn't include signing certificate "…"
```

Pre-flight compares each profile's embedded certs (by SHA-1, which is exactly what
`security find-identity` prints) against the keychain, for **every** bundle ID the
archive embeds (`com.aurahealth.AuraConsumerApp`, its `.AurieWidget` and its
`.IterableNotificationServiceExtension`), and fails in about a second instead. It also
warns when a covering profile is within 30 days of expiry.

To fix it when it fires: import a `.p12` for a cert the existing profiles already
contain, **or unset the three `APP_STORE_CONNECT_*` values and take the Xcode route**,
which needs no certificate at all — usually the cheaper answer.

## Prerequisites

Checked by `plan` in seconds, so none of them can surface deep into an archive:

- `gh` installed and authenticated
- **Clean working tree** — the branch is cut in this checkout and the bump commit must
  carry the version change and nothing else
- **`xcodegen`** on PATH (`make install-xcodegen`) — the `.xcodeproj` is generated, so
  `make proj` runs at the start of every build
- `bundle exec fastlane` runs in **`fastlane/`** (the Gemfile lives there, not at the
  repo root; gems must land in the Ruby named by `.ruby-version`, currently 3.3.12)
- **The env's config files exist** — `AuraConsumerApp/Config/Secrets.<env>.xcconfig`
  and `GoogleService-Info_<Env>.plist`. `make env-<env> release` aborts without them,
  which would be a failure *after* the branch was cut and the bump committed. Both
  destinations it writes are gitignored, so the swap cannot dirty the tree
- **Xcode.app signed into team `9C8CA87JCB`.** On its own, this is the whole credential
  setup for a local release. A personal Apple ID makes xcodebuild reach for a
  development cert and fail during build planning; pre-flight cannot detect the
  wrong-team case, it only shows up in the archive
- **Either** no App Store Connect variables at all (the Xcode route), **or** all three
  in `fastlane/.env` plus an `Apple Distribution` identity in the keychain that an
  installed profile actually contains, for both bundle IDs

> **In a git worktree**, the gitignored config files are absent — `git worktree add`
> cannot bring them across. Pre-flight detects the worktree and says so. Copy them from
> the main checkout per [`.claude/rules/config.md`](../../rules/config.md); the plist
> must be a **real copy, not a symlink**, or xcodebuild omits it from the bundle.
>
> **`fastlane/.env` is one of them, and it is the one that changes behaviour rather
> than breaking it.** With it absent, all three App Store Connect values read as unset
> and the run takes the Xcode route — a *different route than the main checkout* — and
> then dies at the upload with `Failed to Use Accounts`, after the whole archive. So
> pre-flight **blocks** on "linked worktree + no `fastlane/.env` + main checkout has all
> three" and prints the `cp`, rather than passing with the generic Xcode-route warning.
> It only warns when the main checkout has no `.env` either, because that host is
> legitimately on the Xcode route. To take the Xcode route deliberately from a worktree,
> put a worktree-local `fastlane/.env` there with the three values empty.

## Workflow

### 1. Plan — always first

```bash
python3 .claude/skills/release-ios/scripts/release_ios.py plan --env prod --level patch
```

Writes nothing. Prints the resolved version transition, tag, branch, base commit, last
release, the derived phase, every step `run` would take, and any blocking pre-flight
problem. Exit `2` if blocked.

Read three things rather than skimming:

- **The version transition.** `1.29.0 (1) → 1.29.1 (1)` — confirm the baseline matches
  what is actually live.
- **The phase.** `fresh` is a new release. Anything else means a previous run stopped
  part-way and this is a resume.
- **Warnings.** Particularly the `env=dev` one: a dev release still bumps `main` and
  cuts a tag in the shared namespace.

### 2. Show the plan and get approval

**Not optional.** `run` uploads a binary to TestFlight, merges to `main`, and publishes
a GitHub release. Read the consequence sentence `plan` prints at the bottom and state it
back verbatim — it is built from the phase, so on a resume it names only what that run
will actually do:

> *"This uploads `1.29.1-1` to TestFlight, merges a version bump to `main`, tags
> `1.29.1-1` and publishes the `1.29.1-1` GitHub release on
> AuraHealth/AuraConsumerApp."*

Wait for a clear yes.

### 3. Run

The archive runs well past the Bash tool's foreground limit — so **launch it in the
background and poll the log**:

```bash
python3 .claude/skills/release-ios/scripts/release_ios.py run --env prod --level patch > "/tmp/release-ios-$(basename "$PWD").log" 2>&1
```

Use `run_in_background: true`, then `tail` the log. The run is resumable — but see
[Resuming](#resuming) for the one case where "re-run the identical command" is not
enough.

The archive's own output is mirrored to `/tmp/release-ios-<tag>.log`, and on a failed
archive or export the script scans it and prints a **"What actually failed"** block
naming the failing command. Read that instead of scrolling: fastlane ends a failed run
with ~60 lines of its own changelog, so the real error is far above the last thing on
screen.

Useful flags:

| Flag | Use |
|---|---|
| `--skip-build` | The binary is already on TestFlight; do the git half only |
| `--allow-drift` | Merge/tag despite a tree mismatch — see the ordering section |
| `--no-github-release` | Tag without publishing a GitHub release. The release is **on by default**; this opts out |

### 4. Confirm

The script reports the tag, the merge commit, the PR, and the GitHub release URL. It
does **not** confirm App Store Connect finished processing the build — check that in App
Store Connect, and say so plainly rather than reporting the release as fully done.

**The Bugsnag dSYM upload fails the release.** A failed upload raises rather than
warning, and the lane then verifies against the Bugsnag Data Access API that every UUID
in the built dSYM is present and processed — the upload action returning without raising
is not evidence that symbols landed, since it can succeed against the wrong project and
processing happens server-side after the request returns.

Verification needs **`BUGSNAG_TOKEN`** in `fastlane/.env` (a Bugsnag personal access
token, distinct from the notifier API key the upload uses). Without it the upload still
has to succeed, but the run prints a loud unverified warning instead of confirming —
so if you see that warning, the release is back to trusting the upload.

## Resuming

State is derived from git and GitHub every run — there is no state file — so re-running
the identical command picks up wherever it stopped.

⚠️ **With one exception, and it bites exactly where it matters.** The baseline comes from
what `origin/main` declares, so the moment the bump PR merges, main declares the version
being released. A `--level` re-run then computes the version *after* it and starts a
fresh release, walking straight past the unfinished one — which is every phase from
`merged-untagged` onward. **Resume those with the explicit version**, which `plan` prints
for you as a warning whenever it sees a bare tag on origin with no release behind it:

```bash
python3 .claude/skills/release-ios/scripts/release_ios.py run --env prod --version 1.30.0 --build 1
```

```bash
python3 .claude/skills/release-ios/scripts/release_ios.py status --env prod --level patch
```

| Phase | Means | `run` does |
|---|---|---|
| `fresh` | Nothing started | Everything |
| `bumped` | Local branch with the bump; not pushed → **the build did not succeed** | Rebuild, then the rest |
| `branch-pushed` | Branch on origin, no PR → **the binary uploaded** | PR → merge → tag → release |
| `pr-open` | PR awaiting merge | Merge → tag → release |
| `merged-untagged` | Merged, not tagged | Tag → release |
| `tagged-unreleased` | Tag on origin, no GitHub release | `gh release create` only — touches no git state |
| `pr-closed` | PR closed without merging | Blocked — `plan` and `run` both refuse (exit 2). Reopen the PR, or delete the branch and re-run to cut a fresh build |
| `released` | Tag on origin **and** a GitHub release for it | Nothing (exit 0) |

The load-bearing detail: **the branch is pushed only after a successful upload.** That
is what makes "build succeeded, PR failed" distinguishable from "never built" without
querying App Store Connect. Do not push the release branch by hand.

**Resuming never rebuilds.** From `branch-pushed` or `pr-open` the build step is skipped
by phase, so `--skip-build` is redundant there — passing it changes nothing, and
omitting it does **not** trigger a second upload. That flag only matters at
`fresh` / `bumped`.

Because the bump commit lives only in this checkout until it is pushed, a `bumped` phase
is machine-bound — resume on the same host, or delete the branch and start over.

### Waiting at the merge gate

GitHub reports `mergeStateStatus: BLOCKED` both for "a required check failed" and for "a
required check has not finished", so the status alone is not actionable. The script
separates them: a required check still running is waited out (bounded by the 15-minute
merge deadline), while a failed required check or a missing required approval aborts
immediately with the specific reason.

⚠️ **This repo gates `main` with a ruleset, not classic branch protection.** The
`repos/{owner}/{repo}/branches/main/protection` endpoint reports no required checks and
no required reviews, which is simply wrong. The truth lives at
`repos/{owner}/{repo}/rules/branches/main` — currently `ci/circleci: test` and 0
approving reviews, with squash/rebase/merge all permitted. Anything reasoning about
merge requirements must read **rules**.

## CircleCI does not build releases

`.circleci/config.yml` defines `lint` and `test` only. There is no release job, so
nothing double-builds a release this skill cuts. `ci/circleci: test` is the one required
check on the bump PR.

## Exit codes

| Exit | Meaning |
|---|---|
| `0` | Released, or already released (a re-run on a finished release is a no-op) |
| `2` | Blocked or failed — pre-flight problem, drift, closed PR, refused tag |
| `130` | Interrupted; re-run to resume |

## Don't

- **Don't run `bundle exec fastlane release` by hand for a real release.** It ships the
  binary but does not tag, merge, or publish — and nothing then records that the build
  happened.
- **Don't tag by hand after a fastlane run.** The tree checks are the reason the
  build-before-merge ordering is safe; tagging manually skips them, and that is how
  `v1.28.0-1` and `v1.29.0-1` ended up off `main`.
- **Don't hand-write the GitHub release in the web UI.** A tag with no release resumes
  into `gh release create` and nothing else — just re-run the same command.
- **Don't push the release branch by hand** — it is the record that the upload
  succeeded.
- **Don't reach for `--allow-drift` to get past a stopped run.** It answers "the tree
  differs and I know why", not "I want this to proceed".
- **Don't hand-edit `MARKETING_VERSION` in one target only.** The skill refuses to
  release when the two targets disagree.
